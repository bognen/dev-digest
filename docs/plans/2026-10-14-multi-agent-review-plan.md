## Development Plan: Multi-Agent Review (SPEC-07)

### Requirements review

**Source reviewed:** `specs/2026-10-14-multi-agent-review.md` (SPEC-07, `Status: draft`, all OQ-1…OQ-19 resolved by the product owner). I checked its code citations on 2026-10-14 and they hold:
- `agent_runs` has no link to `multi_agent_runs` (`server/src/db/schema/runs.ts`).
- `executeRuns` runs agents one after another in a `for` loop (`server/src/modules/reviews/run-executor.ts`).
- Run rows are created `running` (`repository/run.repo.ts` `createAgentRun`). The boot reaper only reaps `running`.
- The `MultiAgentRun`/`AgentColumn`/`Conflict`/`ConflictTake` contracts in `vendor/shared/contracts/observability.ts` have no importers on either side.
- `RunTraceDrawer` and `FindingCard` import only `@/lib/*`, `@devdigest/ui` and `@devdigest/shared` from outside their own folders, so they can move unchanged.
- `activeKeyFor` already maps `/multi-agent` to key `multi-agent` (`client/src/components/app-shell/helpers.ts`).
- `p-queue` and `@fastify/rate-limit` are already dependencies of `server/`.

**Execution mode:** single-agent pass, decided up front by the caller. No subagent fan-out.

**Clarifications:** none asked. The spec's open-question table is closed, and the code raised no blocking question. The judgment calls I made are listed under "Open questions / assumptions".

**Recommended simplifications / improvements.** These are recommendations to the spec owner. I did not edit the spec. The plan already assumes items 1–6. Item 7 is a code-level fix the plan includes.
1. *(non-blocking, adopted)* **The aggregate status is derived when read and never stored.** One pure function `deriveMultiRunStatus(childStatuses)` (AC-9…AC-11a). There is no aggregate column and no sync logic. AC-18 and NFR-9 then follow from extending the existing boot reaper to also reap `queued` children.
2. *(non-blocking, adopted)* **Minimal schema.** Add two nullable columns on `agent_runs`: `multi_agent_run_id` (FK to the existing `multi_agent_runs`, `ON DELETE SET NULL`) and `multi_agent_position` (AC-7a). Add one index. No new tables. The migration is generated by drizzle-kit.
3. *(non-blocking, adopted)* **Cross-agent grouping and conflict classification are computed in the client, from the multi-run payload.**
   - Why: the payload already carries every child's findings (AC-7), and the grouping is a view concern. Computing it client-side needs no extra contract shapes, and AC-14 holds by construction because the view never writes.
   - Cost: `normalizePath`/`rangesOverlap` (~12 lines) are copied from `server/src/modules/eval/pipeline/scoring.ts`, with a comment citing the source. The server's eval module is private (`no-cross-module`), and the client cannot import server code anyway.
4. *(non-blocking, adopted)* **Estimates return entries only for agents that have data.** An agent with no entry means "no estimate" ("—", AC-21). The client derives everything else.
5. *(non-blocking, adopted)* **The PR-page picker replaces the "Run all enabled agents" item and the per-agent "run now" click.** With every enabled agent preselected, "Run multi-agent review (N)" covers both. The server route `POST /pulls/:id/review` (`all:true`) stays untouched for `mcp-server` (AC-18b).
6. *(non-blocking, adopted)* **Initial child status.** The first `min(N, limit)` children are created `running` and the rest `queued`. This satisfies both AC-1's Verify ("rows still running") and AC-18a's Verify ("2 queued at t≈0" for 6 agents with limit 4).
7. *(blocking for AC-16/AC-17, adopted as a code fix)* **Cancel does not stick today.**
   - The bug: `ReviewService.cancelRun` calls `runBus.cancel()` and then `runBus.complete()`, and `complete()` clears the cancel flag (`platform/sse.ts`). The engine usually never sees the flag. `completeAgentRun(..., 'done')` then overwrites `cancelled` with `done`.
   - The plan's fix: `completeAgentRun` no longer overwrites a row that is already `cancelled` (an extra WHERE condition, no extra round-trip, so NFR-2 still holds).
   - Remaining side effect: a cancelled run whose LLM call had already finished may still persist its review and findings rows.
8. *(non-blocking, recommendation only)* AC-1's Verify says children are `running` while AC-18a introduces `queued`. A later test pass should accept `queued | running` in AC-1.

- The shared Zod contracts (both vendored copies).
- Client data hooks.
- Moving `RunTraceDrawer` and `FindingCard` to a shared client location.

**Rules for every implementer and fix pass:**
- **No tests in this workflow.**
  - Implementers write no new test files or test cases. There is no `test-writer` step.

  - **Exception, existing tests only:** an existing test whose assertions encode behavior the spec deliberately changes may be adapted minimally. This covers the import paths of moved tests, `RunReviewDropdown.test.tsx` (Run all and disabled agents removed) and `nav.test.ts` if it enumerates sections. Adaptation must only remove or update obsolete assertions. Never add cases.

**Post-implementation review, in order:**
1. `architecture-reviewer`, once, over the full diff (server + client).
2. `plan-verifier` in `final` mode, against this plan.

There is no `security-reviewer`, no plan-verifier `steps` pass and no `doc-writer`.

**Fix loop cap: at most 2 fix-pass implementer subagents in total**, shared between architecture-review findings and plan-verifier gaps.
- Only critical/major findings go to a fix pass. Minor ones are reported.
- One fix pass may batch findings from both reviewers.
- After a fix pass, at most **one** re-check runs: a re-run of the reviewer that raised the findings, scoped to the changed files.
- Once the cap is reached, remaining findings are reported to the user and not fixed.

**Total subagent budget:** ≤3 implementers + 1 `architecture-reviewer` + 1 `plan-verifier` (final) + ≤2 fix implementers + ≤1 re-check = **≤8 subagent runs.**
